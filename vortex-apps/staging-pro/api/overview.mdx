The StagingPro V2 Migration API is the control plane behind the **BC Migration** app. Everything
the StagingPro UI does - saving stores, mapping storefront channels, launching bulk or selective
migrations, pausing and resuming runs, streaming live progress - is available over REST, so you can
drive migrations from CI pipelines, scripts, or your own tooling.

## The migration lifecycle

A typical programmatic flow:

<Steps>
  <Step title="Register both stores">
    `POST /api/stores` with the store hash and API token for source and destination. The store's
    real name is pulled from BigCommerce automatically.
  </Step>
  <Step title="Check size before you launch">
    `POST /api/entity-counts` for exact totals, or `POST /api/forecast` for the recommended
    container tier and an ETA for your selected entities.
  </Step>
  <Step title="Create the migration">
    `POST /api/migrations` referencing the saved store ids, the entities to migrate, and a
    conflict strategy (`skip`, `update`, or `replace`). The response returns a `requestId`.
  </Step>
  <Step title="Watch it run">
    Subscribe to `GET /api/migrations/{id}/stream` (SSE) or poll `GET /api/migrations/{id}`.
    Failed and intentionally skipped items are itemised at `GET /api/migrations/{id}/issues`.
  </Step>
  <Step title="Verify the result">
    `POST /api/migrations/{id}/verify` re-runs the same scope read-only and compares source
    against destination without writing anything.
  </Step>
</Steps>

## Safety model

The API enforces the same staging-first guardrails as the StagingPro UI:

- **Production is never a destination.** A store labelled `Production` in the registry is refused
  as a migration destination at the API boundary.
- **A store can never migrate onto itself.** Identical source and destination hashes are rejected.
- **PII requires anonymisation.** Selecting `orders`, `customers`, or `gift_certificates` requires
  `anonymise_customer_data: true`.
- **Runs are resumable and auditable.** Every run checkpoints continuously; pause, resume, and
  cancel are first-class operations, and the issue log records every failed or skipped item.

## Modes

| Mode | What it does |
| --- | --- |
| `full` | Migrates the selected entities (the default). |
| `dry-run` | Walks the full migration without writing to the destination. |
| `verify` | Read-only source vs destination comparison. |
| `counts` | Entity totals only. |
