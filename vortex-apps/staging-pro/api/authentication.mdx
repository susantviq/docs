title: "Authentication"
description: "How to authenticate against the StagingPro V2 Migration API - organisation scoping today, and the planned OAuth token endpoint."
---

The StagingPro V2 Migration API is served from `https://app.vortexiq.ai/v2/api/bc-migration`. Every
request is authenticated as a Vortex IQ user and scoped to a single organisation.

## Today: your signed-in session

Requests are authorised using your Vortex IQ session, the same one the StagingPro UI uses. If you
are signed in to `app.vortexiq.ai` in the browser, calls from that page are already authenticated:

```js
// From a signed-in app.vortexiq.ai page - the session cookie travels automatically.
const res = await fetch('/v2/api/bc-migration/migrations');
const { migrations } = await res.json();
```

Two conditions must hold for any call to succeed:

<Steps>
  <Step title="You are signed in">
    Requests without a valid session are rejected.
  </Step>
  <Step title="Store Migration is enabled for your organisation">
    The app is enabled per organisation. If yours is not on the list, every endpoint returns `403`:

    ```json
    { "message": "Store Migration is not enabled for this organization." }
    ```

    Contact [support](https://www.vortexiq.ai/contact-us) to have it enabled.
  </Step>
</Steps>

Everything you read or start is scoped to your organisation. Migration history shows only your
organisation's runs, and a store must be connected to your organisation before you can migrate it -
otherwise you get `422 store_not_found`.

<Note>
  **Server-to-server calls are not supported yet.** Session authentication is designed for calls
  made from a signed-in browser context. If you need to drive migrations from CI or a backend
  service, the OAuth flow below is the supported path once it ships - please wait for it rather
  than automating a browser session.
</Note>

## Coming soon: OAuth tokens

<Warning>
  **Planned - not yet available.** The `/login` endpoint described here is not live. The shape below
  is indicative and may change before release; this section will be updated with the final contract
  when it ships.
</Warning>

A dedicated token endpoint is planned so that scripts and backend services can call the API without
a browser session:

```
POST https://app.vortexiq.ai/v2/api/bc-migration/login
```

It will exchange your **user**, **organisation id**, and an issued **key** for an OAuth token, which
you then send as a bearer token on subsequent requests:

```bash
# Planned - illustrative only.
curl -X POST https://app.vortexiq.ai/v2/api/bc-migration/login \
  -H "Content-Type: application/json" \
  -d '{ "user": "<user>", "org_id": "<organisation-id>", "key": "<issued-key>" }'

# Then, on every call:
curl https://app.vortexiq.ai/v2/api/bc-migration/migrations \
  -H "Authorization: Bearer <token>"
```

The same organisation gate applies: a token is only ever valid for the organisation it was issued
for, and only if Store Migration is enabled for it.

## Store credentials

You never send BigCommerce API tokens to this API.

Stores are referenced by **store hash** - for example `"source_store_hash": "abc123xyz"`. Vortex IQ
resolves each store's BigCommerce credentials server-side from your organisation's connected
StagingPro integrations, and authorises the store against your organisation on every call. Tokens
never travel through the browser, your scripts, or this API's request bodies.

This is why connecting a store in StagingPro is a prerequisite for migrating it, and why a hash your
organisation has not connected returns:

```json
{
  "error": "store_not_found",
  "message": "source or destination store not found / not authorized for this organization"
}
```

## Errors you may hit

| Status | Meaning |
| --- | --- |
| `403` | Not signed in, or Store Migration is not enabled for your organisation. |
| `422` | A store hash is unknown or not connected to your organisation, or the request failed validation. |
| `502` | The migration service or BigCommerce could not be reached. |
