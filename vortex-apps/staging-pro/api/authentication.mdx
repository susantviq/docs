title: "Authentication"
description: "How requests to the StagingPro V2 Migration API are authenticated - the X-Proxy-Key edge key, the X-Support-Key for diagnostics, and X-Org-Id organisation scoping."
---

The StagingPro V2 Migration API uses header-based keys at two levels. All keys travel over HTTPS
only.

## X-Proxy-Key (all endpoints)

Every `/api/*` call except [Health check](/vortex-apps/staging-pro/api/health) must carry the edge
key:

```bash
curl https://stagingpro-v2.vortexiq.ai/api/stores \
  -H "X-Proxy-Key: <your-proxy-key>"
```

When you use StagingPro through the Vortex IQ platform, the platform proxy injects this header for
you - you never handle it directly. It is required explicitly only when calling the control plane
directly (self-hosted or programmatic access).

A missing or invalid key returns `401`:

```json
{ "error": "unauthorized", "message": "valid X-Proxy-Key required" }
```

## X-Support-Key (diagnostics endpoints)

The [Knowledge Base](/vortex-apps/staging-pro/api/get-knowledge) and
[Support Diagnostics](/vortex-apps/staging-pro/api/get-migration-support) endpoints are gated by an
additional support key, passed as a header or query parameter:

```bash
curl https://stagingpro-v2.vortexiq.ai/api/knowledge \
  -H "X-Proxy-Key: <your-proxy-key>" \
  -H "X-Support-Key: <your-support-key>"
```

A missing or invalid support key returns `403`:

```json
{ "error": "support_only", "message": "valid support key required" }
```

## X-Org-Id (organisation scoping)

When calls arrive through the Vortex IQ platform, the proxy also injects `X-Org-Id`. Runs created
with an org context belong to that organisation; reading or controlling a run that belongs to a
different organisation returns `404` (not `403`), so run ids are never confirmed across tenants.

Direct calls without `X-Org-Id` operate unscoped - intended for single-tenant, self-hosted
deployments and support tooling.

## BigCommerce store tokens

Store API tokens are supplied once when [registering a store](/vortex-apps/staging-pro/api/add-store)
and are held server-side:

- Tokens are **never returned** by any endpoint - store objects expose only a `tokenSet` boolean.
- Migration run credentials live only in the run directory for the lifetime of the run and can be
  wiped on completion; resume and verify re-inject them from the registry when needed.
