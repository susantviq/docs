This page combines three closely-related migration topics: BigCommerce B2B Edition migration support, the rules around coupon and promotion migration, and the broader data dependency map you need to read before running any partial migration.

# B2B Edition support

B2B Edition (formerly Bundle B2B) adds a parallel data model on top of standard BigCommerce: company roles, companies, addresses, users, super admins, and sales staff. StagingPro V2 migrates it from the **B2B Edition Migration** panel on the Bulk Content Migration page.

## What migrates

| B2B entity family | What it covers |
| --- | --- |
| **Roles & Permissions** | Company roles and their permission sets |
| **Companies** | Company records including status, payment configuration, parent/child company hierarchy, and price-list links |
| **Company Addresses** | Addresses attached to each company |
| **Company Users** | The buyers belonging to each company |
| **Super Admins** | Super admin accounts and their company assignments |
| **Sales Staff Assignments** | Sales-rep-to-company assignments |

**Not included** (deliberate scope, planned for a follow-up): B2B orders, invoices, quotes, and shopping lists.

Existing destination companies with the same identity are matched and updated rather than duplicated, and destination-only companies are never deleted.

## Prerequisites

<Steps>
  <Step title="B2B Edition on both stores">
    Both the source and destination stores must have the B2B Edition app installed and activated by BigCommerce. The panel only appears when both stores are B2B; if either isn't, it is hidden entirely.
  </Step>
  <Step title="A store API token with the B2B Edition scope">
    There are **no separate B2B credentials** — the store's main API token does everything, provided it was created with the **B2B Edition** access level. Token scopes are fixed at creation, so an existing token without B2B access must be replaced: create a new **store-level API account** (BigCommerce control panel → Settings → Store-level API accounts) with the B2B Edition scope.

    <Warning>
      Tokens created inside the B2B Edition app's own "API accounts" page do **not** work for migration — it must be a store-level API account. If a store is B2B but its token lacks B2B access, StagingPro shows a plain-language "B2B entities can't be migrated yet" card naming the store and the fix.
    </Warning>
  </Step>
  <Step title="Anonymisation for personal data">
    Companies, Company Addresses, Company Users, and Super Admins carry personal data, so they stay locked until the shared **Anonymise Customer Data** switch (the same one that covers orders) is on. Anonymised identity is stable, so repeat runs match earlier copies and never create duplicates. Roles & Permissions and Sales Staff Assignments are always available.
  </Step>
</Steps>

<Note>
  **Classic app users:** the old **Settings → B2B Edition** tab, where a dedicated B2B user email and password were entered per environment, is obsolete in V2 — any values entered there are ignored, and the tab is slated for removal. V2 authenticates B2B entirely through the store's main API token.
</Note>

## B2B entity dependencies

Companies link to **Customer Groups** and **Price Lists**, and Company Users link to **Customers** — migrate those (or make sure they already exist on the destination) for the company relationships to resolve fully. Migrate B2B entities together with, or after, the core catalogue and customer data; the B2B phases run last in a bulk migration for exactly this reason.

# Coupons and Promotions

Coupon codes in BigCommerce are part of the Promotions system. When you migrate a promotion via StagingPro:

- Product, category, brand, and customer-group references inside the promotion are re-pointed at the matching items on the destination.
- A promotion whose reference cannot be mapped is **skipped with a clear reason rather than migrated with broadened scope** — a discount is never silently widened to more products than it covered on the source.
- Coupon codes attached to a promotion travel with the promotion (and are not duplicated as legacy coupons).
- Storefront-scoped promotions land on the mapped storefronts; if none of the promotion's storefronts are mapped, it is skipped with the storefront named.

### Promotions migrate in their entirety

There is no partial migration of an individual promotion's rules. Each promotion moves as a complete unit including all conditions, actions, schedule, and notifications.

<Warning>
  ### Promotions created via API cannot be edited after creation

  This is a BigCommerce constraint. If a promotion was originally created via the API and you discover the rules need adjusting on the destination, the workaround is to delete the promotion in the source, recreate it correctly, and re-migrate. We will surface manual editing once BigCommerce supports it natively.
</Warning>

## Data dependencies, the full map

Some entities depend on others being present so their references resolve on the destination:

| Migrating entity | How dependencies are handled |
| --- | --- |
| Products (selective) | The brands and categories the picked products reference are migrated automatically (with category ancestors) |
| Product Reviews / Bulk Pricing / Metafields | Ride with their product |
| Channel Assignments | Need the storefront (channel) mapping |
| Product Locale | Needs the destination storefront configured with the same locales |
| Category Metafields | Ride with their category |
| Price List Records & Assignments | Need Price Lists and Customer Groups |
| Customers | Need Customer Groups |
| Shipping Methods | Need Shipping Zones |
| Promotions | References resolve against items already migrated or already on the destination; unmappable references cause a reasoned skip |
| Search contextual filters, 301 redirects | Remap through category/product/brand/page references — migrate those entities in the same run (or earlier) |

### Why this matters

On a **selective** run, dependencies come along automatically (a product pick brings its brands and categories). On a **bulk** run, you choose the entity groups explicitly — the engine re-points cross-entity references through whatever the run migrated *or what already exists on the destination*, and drops what it can't resolve with a warning. If you only want to move promotion configuration without touching the catalogue, the products, categories and customer groups it references must already exist on the destination.
