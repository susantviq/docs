> Count of transactions where debits do not equal credits. NetSuite rejects imbalanced transactions, so any persistence here means an integration is generating malformed postings on the calling side.

## At a glance

{/* HUMAN_AUTHORED:tldr */}
> The number of transactions that failed to balance, where total debits do not equal total credits. In a healthy account this is zero, always, because NetSuite refuses to save a transaction that does not balance. A non-zero reading is not an accounting problem inside NetSuite; it is a sign that an external integration calling NetSuite is constructing malformed postings and the calls are being rejected. The fix is never in NetSuite, it is in the code on the calling side.

| | |
| --- | --- |
| **What it counts** | Transactions detected as failing the debit-equals-credit rule: rejected save attempts, partially-written transactions, and any line where the journal does not foot to zero. |
| **Healthy value** | Zero. This card is a defect detector, not a business metric. |
| **What non-zero means** | An integration (SuiteScript, REST/SOAP web service, CSV import or middleware) is sending an unbalanced transaction; NetSuite rejects it, but the order, invoice or payment behind it did not post. |
| **Currency** | n/a. The headline is a count; rounding mismatches that cause imbalances are usually currency-related. |
| **Subsidiary scope** | Respects dashboard filter. On OneWorld, imbalances are attributed to the originating subsidiary. |
| **Time window** | `RT` (live count of currently-detected imbalances) |
| **Alert trigger** | Count greater than 0 |
| **Roles** | owner, finance, engineering |
| **Chart type** | KPI count with the originating integration and transaction type listed beneath |

## Calculation

Calculated automatically from your NetSuite data and the integration error surface. The card counts transactions where the fundamental double-entry rule is violated: total debits do not equal total credits. NetSuite enforces this rule at save time, so a truly imbalanced transaction is rejected rather than stored, which is why the healthy value is zero. The card therefore reads the failure surface (rejected saves, SuiteScript errors that report a balancing failure, and partially-written records) rather than expecting to find balanced-but-wrong rows sitting in the ledger.

A non-zero count is a hard integration-defect signal, not a soft accounting drift. It means a calling system is building a posting incorrectly, and the business event behind that posting (an order, an invoice, a payment, a journal) did not land. See the At a glance summary above for what feeds the count and the worked example below for how to trace one back to its source.

## Worked example

{/* HUMAN_AUTHORED:worked_example */}
A US consumer-electronics brand on NetSuite OneWorld. US parent (USD) ingests Shopify orders via a middleware connector; a UK sub (GBP) ingests BigCommerce orders. Custom SuiteScript posts marketplace settlement journals. Annual revenue ~$70M. Reading taken 12 Jun 26. Reporting currency USD.

| Source integration | Transaction type | Imbalances detected | Likely cause |
| --- | --- | --- | --- |
| Marketplace settlement SuiteScript | Journal Entry | 5 | Rounding on multi-line FX split, lines foot to a 0.02 difference |
| Shopify middleware | Cash Sale | 2 | Tax line dropped on discounted orders |
| Manual CSV import | Journal Entry | 1 | Pasted figures, one debit line transposed |
| BigCommerce middleware | Customer Invoice | 0 | Healthy |
| **Transaction Imbalances (this card)** | | **8** | |

Five things to notice:

1. **Eight is eight too many, because the only acceptable reading on this card is zero.** Unlike almost every other KPI in the Nerve Centre, there is no "healthy range" here and no nuance about thresholds: a non-zero count is by definition a set of failed business events. The alert fires above zero precisely because there is no benign non-zero value. The reason this is a hero card is that each imbalance represents a transaction that did not save, which means an order without revenue, an invoice that was never raised, or a payment that was never recorded. The count looks small, but each unit is a hole in the books that someone has to find and patch manually.

2. **The card points at the integration, not at NetSuite, and that distinction is the whole value of the card.** NetSuite did its job perfectly: it refused to store an unbalanced transaction, which is exactly what a ledger should do. The defect lives entirely on the calling side, in the SuiteScript, the middleware or the import that constructed the bad posting. So the action is never "fix the data in NetSuite", it is "fix the code that builds the posting". The card lists the originating integration and transaction type beneath the count for exactly this reason: it routes the engineer straight to the malformed caller, not the finance team to a phantom ledger entry that does not exist because it was rejected.

3. **The five settlement-journal imbalances footing to a 0.02 difference are the classic FX-rounding defect.** When a SuiteScript splits a multi-currency settlement across several lines and rounds each line independently, the rounded lines can fail to foot to zero by a cent or two. NetSuite rejects the whole journal because two cents of imbalance is still an imbalance. The fix is a standard accounting pattern: route the rounding residual to a designated rounding or FX-gain-loss line so the journal always balances to the penny. This is the single most common cause of a persistent low-level imbalance count on accounts that post multi-currency journals via script, and it is invisible until a card like this surfaces it.

4. **The two dropped-tax-line Cash Sales are the most expensive kind of imbalance, because they are silent revenue loss.** When the Shopify middleware drops the tax line on discounted orders, the Cash Sale does not balance and NetSuite rejects it, which means the order's revenue never posted. The customer was charged on Shopify, the cash will land in the bank, but NetSuite has no record of the sale, so it shows up nowhere in revenue, nowhere in tax liability, and nowhere in the customer's history. This is the failure mode that connects this card to the [Commerce Orders Without a NetSuite SO](/nerve-centre/kpi-cards/netsuite/commerce-orders-without-netsuite-so) reconciliation: an imbalance is one of the reasons a captured order never becomes a posted transaction.

5. **A persistent non-zero count is a worse signal than a one-off spike, because it means the bug is structural.** A single imbalance from a fat-fingered CSV import is a human error: annoying, easily fixed, unlikely to recur. Five imbalances every day from the same settlement script is a structural defect that will keep dropping transactions until the code is fixed, and the cumulative hole in the books grows daily. This is why the card reads live and the [NetSuite Health Score](/nerve-centre/kpi-cards/netsuite/netsuite-health-score) weights any non-zero imbalance hard into its integration pillar. The pattern of the count over time tells you whether you are looking at noise (occasional, varied sources) or a fault (persistent, single source). The persistent single-source pattern is the one that demands an engineering ticket today.

## Reconciling against NetSuite

{/* HUMAN_AUTHORED:reconcile */}
**Where to look in NetSuite:**

Because NetSuite rejects imbalanced transactions rather than storing them, you will not find imbalanced rows sitting in the ledger. You reconcile this card against the error and execution surfaces, not against a transaction report. The relevant native views:

> **Customization → Scripting → Script Execution Log** (filtered to errors; balancing failures from SuiteScript appear here with the failure message)
> **Setup → Import/Export → View CSV Import Status** (failed import rows, including those rejected for not balancing)
> **System Notes** on the affected records, where a partial write left a trace
> **Reports → Financial → General Ledger** run with a balance check, which should always foot to zero (if it does not, that is a far more serious integrity issue than a rejected save)
> **Setup → Integration → Web Services Usage Log** (REST/SOAP calls that returned a balancing error to the caller)

The reconciliation mindset is inverted from most cards: a healthy NetSuite shows nothing here because the bad transactions were rejected. The card's value is surfacing the rejections that would otherwise be buried in a script log nobody reads.

**Why our number may legitimately differ from what you find in the logs:**

| Reason | Direction | Why |
| --- | --- | --- |
| **Retry success** | Card may read lower | An integration that fails once and retries successfully created a log error but no lasting imbalance; the card focuses on unresolved failures, the log shows every attempt. |
| **Aggregation of attempts** | Card may read lower | Multiple log lines from repeated retries of the same transaction count as one underlying imbalance to the card, but as many lines in the execution log. |
| **Detection latency** | Either | A failure that occurred and was corrected between samples may not register; the card samples live rather than tailing every log line. |
| **Non-balancing errors in the same log** | Card may read lower | The script execution log contains many error types; the card isolates balancing failures specifically, so it will be lower than a raw error count. |
| **Manual corrections** | Card may read lower | If finance manually keyed the correct balanced transaction after a rejection, the business event is now recorded even though the original call failed. |
| **Middleware-side rejections** | Card may read lower | Some malformed transactions are caught by middleware before reaching NetSuite, so they never hit the NetSuite logs; the card sees only what reached NetSuite. |
| **Subsidiary attribution** | Either | An imbalance from a shared integration is attributed to the originating subsidiary; a manual log review may group differently. |

**Cross-connector reconciliation:**

This card sits at the boundary between the commerce connectors and NetSuite, because the most damaging imbalances are commerce transactions that failed to post. NetSuite alone shows the rejection; the commerce platform alone shows a captured order; only the join shows that the captured order has no corresponding posted transaction.

| Card | Expected relationship | What the comparison reveals |
| --- | --- | --- |
| [Commerce Orders Without a NetSuite SO](/nerve-centre/kpi-cards/netsuite/commerce-orders-without-netsuite-so) | Overlapping cause | An imbalanced Cash Sale or invoice is one reason a commerce order never becomes a posted NetSuite transaction; the two cards often light up together. |
| [shopify.orders](/nerve-centre/shopify/orders) | Source of truth on capture | Shopify shows the order was captured and the customer charged; if the matching NetSuite transaction was rejected for imbalance, money moved but no posting exists. |
| [bigcommerce.orders](/nerve-centre/bigcommerce/orders) | Source of truth on capture | Same dynamic for BigCommerce; a drop in posted transactions against steady BC orders points at a posting defect. |
| [NetSuite Health Score](/nerve-centre/kpi-cards/netsuite/netsuite-health-score) | Drives the integration pillar | A non-zero imbalance is one of the cleanest, least-ambiguous inputs to the health score's integration-error-free pillar. |

The killer cross-channel framing is that an imbalance is a transaction that exists on the commerce side and is missing on the finance side. The storefront shows a charged order; NetSuite shows nothing, because the posting was rejected. Neither system, alone, can tell you that real money moved without a corresponding ledger entry. Vortex IQ holds both, so it can pair the captured commerce order with the rejected NetSuite posting and surface the gap as a single number before the cash hits the bank unexplained at the next reconciliation. That is the difference between catching the defect the day it starts and discovering an unexplained cash variance three weeks later at close.

## Known limitations / merchant FAQs

{/* HUMAN_AUTHORED:faqs */}
**If NetSuite rejects imbalanced transactions, how can this number ever be non-zero?**
Because the card counts the rejections, not stored imbalanced rows. NetSuite is correct to refuse an unbalanced transaction, and it never stores one. What it does do is fail the save attempt, log an error, and return a failure to the calling integration. The card surfaces those failed attempts. So a non-zero reading does not mean your ledger is unbalanced (it is not, NetSuite guarantees that); it means business events are being rejected before they can post, which is arguably worse, because the data is simply missing.

**So is this a NetSuite problem or my integration's problem?**
Almost always your integration's problem. NetSuite enforcing double-entry is the system working as designed. The defect is in whatever is constructing the posting: a SuiteScript that rounds FX lines independently, a middleware that drops a tax line, a CSV with a transposed figure. The fix is in the calling code, not in NetSuite settings. This is why the card lists the originating integration and transaction type: it routes the engineer to the malformed caller.

**What is the single most common cause?**
Multi-currency rounding in scripted journals. When a script splits a settlement or an inter-company posting across several lines and rounds each line independently, the lines can fail to foot to zero by a cent or two, and NetSuite rejects the whole journal. The standard fix is to route the rounding residual to a dedicated rounding or FX-gain-loss line so the journal always balances exactly. If you post any multi-currency journals via SuiteScript, this is the first place to look.

**OneWorld and subsidiaries, how are imbalances attributed?**
Each imbalance is attributed to the originating subsidiary, which is the entity the failed transaction belonged to. On OneWorld, inter-company journals are a frequent source because they touch two subsidiaries and must balance within and across them; an inter-co posting that balances on one side but not the other will be rejected. Read the count per subsidiary to localise the failing integration, especially when a shared script posts to multiple subs.

**FX and multi-currency, why does it cause so many imbalances?**
Because converting amounts between currencies introduces rounding, and rounding several lines independently breaks the foot-to-zero rule. A single-currency transaction rarely imbalances unless a line is genuinely wrong; a multi-currency transaction can imbalance purely from rounding even when every figure is conceptually correct. The fix is a rounding line, not different exchange rates. This is the cleanest example of an imbalance that is a code defect rather than a data-entry error.

**Does period close cause a spike?**
It can. Close periods involve more manual journal entries, more accruals and reversals, and more inter-company postings, all of which are higher-risk for hand-keyed or scripted imbalances. A small rise during close is often human entry error on manual journals; the fix is the same (find the unbalanced line) but the source is a person, not a system. Read this card more attentively during close week.

**How does this relate to manual journal entries?**
Manual journals are a leading source of hand-keyed imbalances, because a human entering debits and credits by hand can transpose a figure or miss a line. The more of your GL activity comes from manual journals (see [Manual Journal Entries as % of Total](/nerve-centre/kpi-cards/netsuite/manual-journal-entries-as-of-total)), the more opportunities there are for a hand-keyed imbalance. A high manual-JE share and a non-zero imbalance count together point at process risk in the manual-entry workflow.

**Can a rejected transaction silently lose me revenue?**
Yes, and this is the most important reason the card is a hero. If a Cash Sale or Customer Invoice is rejected for imbalance, the revenue behind it never posts. The customer may still have been charged on the storefront, so cash arrives with no matching sale recorded. The order shows nowhere in revenue, the tax liability is understated, and the customer's purchase history is incomplete. This connects directly to the commerce-orders-without-a-NetSuite-SO reconciliation, where rejected postings are one of the root causes.

**What should I do the moment the count goes above zero?**
Read the originating integration and transaction type listed beneath the count, then go to that integration's error surface (script execution log for SuiteScript, import status for CSV, web services log for API calls). Identify whether it is a one-off (human error, single source, varied) or a pattern (persistent, single source, same type). A one-off gets corrected manually. A pattern gets an engineering ticket today, because it will keep dropping transactions and growing the hole in the books until the calling code is fixed.

**Does SuiteScript ever cause imbalances even when the logic looks correct?**
Yes, most often through independent line rounding, as described, and occasionally through a script that builds a transaction conditionally and skips a line under an edge case (a discounted order, a zero-tax jurisdiction, a fully-comped line). The logic can look correct for the common path and fail on an edge case that only occurs occasionally, which is why the imbalance appears intermittently. Trace it by correlating the failures against the attributes of the orders that triggered them; the edge case is usually obvious once you see the pattern.

**NetSuite versus other ERPs, do they all reject imbalanced transactions?**
Every double-entry accounting system enforces debit-equals-credit at the transaction level, so SAP S/4HANA, Oracle ERP Cloud and any GAAP-compliant ERP will all reject an unbalanced posting just as NetSuite does. What differs is the integration surface: the NetSuite specifics are SuiteScript, the SuiteTalk web services and CSV import, whereas SAP uses IDocs and BAPIs and Oracle uses its integration framework. The card concept is portable to any ERP; the originating-integration detail is NetSuite-shaped. In all cases the lesson is the same: the ERP is not the problem, the malformed caller is.
